Stripe Billing vs Chargebee vs Lago: The Real Engineering Cost of Usage-Based Metering

📅 Nov 18, 2026  |  Category: Technology  |  Read Source →

Posted on Nov 18 • Originally published at lumeir.online

Originally published at Lumeir Systems Lab. For interactive architecture schematics, SVG topology diagrams, and 12-month FinOps cost tables, examine the complete empirical audit on Lumeir.

The technical transition from traditional seat-based SaaS subscriptions to usage-based pricing models represents a radical shift in database access patterns, distributed system boundaries, and financial accounting guarantees. In a legacy seat-based system, state changes occur infrequently. A user is created, a plan is upgraded, or a seat is revoked. These operations execute over synchronous REST calls, mutating a handful of rows inside a standard relational database with strict ACID guarantees. System throughput requirements rarely exceed a few dozen operations per second, even for enterprise-scale platforms.

Usage-based metering completely shatters this low-frequency paradigm. When pricing is tied directly to API calls, compute seconds, gigabytes ingested, or transactional volume, the billing architecture transitions from a passive administrative system into a high-throughput stream processing network. Every single user request across your application cluster must generate an immutable, audit-compliant event. If your system handles 50,000 API requests per second, your metering pipeline must ingest, deduplicate, aggregate, and store 50,000 financial events per second without dropping a single byte or introducing unbearable tail latencies into the critical request path.

Superficial vendor marketing frequently collapses this engineering problem into simplified API documentation, selling the illusion that billing integration is merely a matter of firing a HTTP POST payload to an external REST endpoint. In production, this abstraction breaks down immediately. Naively wrapping external vendor HTTP calls inside your API request paths causes severe thread pool exhaustion, socket starvation, and cascading failures during traffic spikes. Conversely, attempting to aggregate events locally without strict distributed idempotency guarantees leads to double-billing bugs or untraceable revenue leakage.

Choosing between platform-as-a-service billing engines like Stripe Billing and Chargebee, or open-source infrastructure like Lago, is not a simple comparison of feature sets or dashboard aesthetics. It is a fundamental choice between radically different architectural trade-offs: external API serialization overhead versus self-hosted event queue maintenance, percentage-based gross revenue take-rates versus operational infrastructure cost, and rigid black-box ledger semantics versus fully inspectable database write paths.

To evaluate these platforms accurately, we must analyze the execution paths of their ingestion engines, thread models, storage mechanics, and protocol overhead when processing high-frequency usage events.

Stripe Billing handles usage-based metering primarily through its Meter Events API. The architectural path of a meter event within Stripe relies on a globally distributed, highly resilient multi-tenant infrastructure built atop distributed storage systems. When an application dispatches a POST request to Stripe's metering endpoint, the payload passes through an edge proxy tier running ingress TLS termination, a path sensitive to edge compute cold start latency, before reaching the internal routing mesh.

Stripe forces network communication over standard HTTPS REST interfaces utilizing JSON payloads. Under heavy load, this protocol choice incurs substantial serialization overhead and HTTP/1.1 or HTTP/2 frame overhead compared to binary protocols like gRPC or native TCP streaming. Within Stripe's backend, event ingestion is immediately separated from aggregation logic. The ingress engine performs lightweight validation (checking API key signatures, rate limits, and payload schemas) and appends the raw event to a distributed append-only log backed by highly available stream infrastructure.

Idempotency in Stripe is enforced via an explicit identifier parameter attached to the meter event. To verify whether an event key has already been processed within a rolling window, Stripe utilizes an internal distributed key-value cache layer (optimized for low-latency point lookups, as detailed in our distributed key-value cache latency benchmarks). If the key exists, the event is safely ignored, returning an HTTP 200 response with the existing event payload status. If the key is unique, the event is appended to the stream for async processing.

The primary constraint of Stripe's architecture is the black-box nature of its aggregation compute cycle. Events sent to Stripe are aggregated asynchronously in background batch windows. While this shields Stripe's external API from database lock contention during ingestion, it introduces a propagation delay between event emission and invoice balance visibility. Additionally, because Stripe charges a fee on gross processed volume, application developers must evaluate whether paying a percentage-based tax on every metered dollar is architecturally justified when operating high-volume, low-margin infrastructure.

Chargebee's heritage lies in traditional subscription lifecycle management. Its usage-based metering implementation is built atop an architecture historically designed around relational account objects. Usage data in Chargebee is typically ingested through the Chargebee Usage API or bulk import routines, which mutate billing subscriptions via internal service layers.

Unlike Stripe's modern decoupled event-stream ingestion architecture, Chargebee's runtime execution path exhibits tighter coupling to relational database state. When usage data is pushed to Chargebee, the engine validates the usage against the active customer subscription record. This process often triggers synchronous or near-synchronous relational database updates to compute cumulative plan usage, remaining credit balances, and tiered soft limits.

Because Chargebee relies heavily on multi-tenant relational database clusters, high-frequency event ingestion creates severe write amplification. Each incoming usage record must update internal tracking tables, execute index balance checks, and write to transactional database log sequences. Under sustained ingestion rates exceeding hundreds of operations per second per account, this architecture experiences lock contention on subscription rows. To prevent database degradation, Chargebee enforces strict API rate limits and encourages developers to perform pre-aggregation inside their application layer before pushing summarized usage metrics in periodic batches.

This limitation forces the application developer to build and maintain an in-house pre-aggregation engine (such as Redis RedisStream or Apache Flink, with high-throughput data orchestration platforms providing the pipeline layer) merely to protect Chargebee from being overwhelmed by raw usage volume. Consequently, Chargebee functions less as a high-throughput event meter and more as a periodic usage synchronization system for downstream invoice rendering.

Lago approaches usage-based metering from a modern stream-processing perspective. Architected as an open-source, deployable stack (as well as a managed cloud service), Lago explicitly separates high-speed event ingestion from heavy ledger computation through a micro-component model composed of an API ingress layer, Redis stream/queue workers, PostgreSQL persistent storage, and background processing workers written in Go and Ruby.

In Lago's self-hosted architecture, incoming events hit a dedicated Go-based API routing tier designed for minimal memory allocation and rapid request termination. When a meter event reaches Lago via the /api/v1/events endpoint, the engine does not perform inline relational database writes. Instead, it executes an atomic cache check using Redis to evaluate the event's unique transaction identifier for idempotency.

If the transaction identifier is novel, Lago pushes the raw event into a Redis-backed buffer stream and immediately returns an HTTP 202 Accepted response to the client application. This design keeps p99 ingress API latency consistently under 10 milliseconds, as the request thread never waits on disk I/O or complex ledger calculation.

Background worker processes pull batches of events from the stream queue, applying sliding-window temporal aggregations (such as SUM, COUNT, MAX, or UNIQUE COUNT) defined by the system's billable metrics. The resulting aggregate counts are written in optimized bulk transactions to PostgreSQL. This decoupled write path eliminates row-level database locking during live traffic spikes. Because Lago can be compiled and deployed directly within an organization's private cloud infrastructure (AWS EKS, GCP GKE, or bare-metal Kubernetes), internal application services communicate with Lago over low-latency, private VPC network interfaces, avoiding the public internet network transit latency inherent to third-party SaaS vendors.

To quantify the real-world operational capabilities of each platform under load, we executed a rigorous 24-hour benchmark simulation. The test harness simulated a high-throughput API gateway pushing usage events generated by 10,000 active customer accounts. The benchmark environment consisted of a target ingestion load of 10,000 API meter events per second with intermittent bursts reaching 25,000 events per second to evaluate system resilience under acute traffic spikes.

The benchmark data reveals drastic divergence in latency profiles and scaling limits between the three architecture types.

Chargebee's architecture encountered severe bottlenecks at relatively low throughput scales. Once request rates surpassed 450 events per second, the service returned HTTP 429 Rate Limit errors. Tail latency degraded significantly, with P99 latencies spiking to 1,240 milliseconds. This performance drop is directly attributable to synchronous validation logic and relational row-level lock contention within Chargebee's database tier. Attempting to stream raw API usage directly to Chargebee without pre-aggregating data in an internal application buffer is practically impossible at enterprise scale.

Stripe Billing demonstrated superior resilience compared to Chargebee, handling sustained ingestion up to 2,500 events per second per endpoint connection before hitting account-level concurrency throttles. P50 latency remained consistent at 48 milliseconds, but P99 latency deteriorated to 485 milliseconds under peak traffic bursts. The primary bottleneck for Stripe is not system crash failure, but network transport overhead and WAN propagation latency. Every event sent to Stripe requires an outbound public HTTPS connection, which incurs TLS handshake verification, TCP slow-start parameters, and serialization penalties. At high volumes, these network hops impose a non-negligible CPU and latency tax on the host application.

Self-hosted Lago achieved the highest throughput and lowest tail latencies by a wide margin. In default configurations, Lago sustained 12,500 events per second with a P99 latency of 28 milliseconds. After applying custom kernel, Redis, and PostgreSQL tuning parameters (including connection pooling, disabled synchronous commits on non-critical log streams, and extended memory allocation for the Go ingress workers), Lago handled peak loads of 24,000 events per second with P99 latencies dropping to 16 milliseconds.

The underlying reason for Lago's extreme throughput advantage lies in its storage engine interaction model. By using Redis as a lockless ingest buffer, Lago decouples client-facing HTTP response execution from persistent disk writes. The write amplification factor on PostgreSQL remains extremely low because background workers aggregate thousands of in-memory events into single bulk INSERT ... ON CONFLICT SQL operations, drastically reducing Write-Ahead Log (WAL) I/O strain.

Selecting a usage-based billing infrastructure is an architectural decision with direct impact on long-term gross margins. Platform take-rates that seem negligible at $50,000 in Monthly Recurring Revenue (MRR) convert into severe financial drag once throughput scales to tens of millions of usage events. The financial trade-off reflects fundamental architectural differences. Stripe Billing and Chargebee charge a variable tax tied directly to gross processing volume. As top-line revenue scales, your billing infrastructure costs scale linearly regardless of actual compute utilization. A high-margin API company processing high-volume, low-margin events (such as AI vector processing or log ingestion) can easily see 15% to 25% of their unit margin consumed entirely by vendor billing take-rates.

Conversely, self-hosting an append-only event engine like Lago decouples processing volume from financial margin. Compute and storage overhead scale with raw event count and event payload byte size, not with the dollar value of the invoice line-item. The initial engineering investment in managing Kafka event stream topics and ClickHouse aggregations yields massive structural savings once gross revenues cross the $10,000,000 threshold.

Deploying high-throughput usage metering into production exposes structural limits across database layers, network sockets, and process memory limits. The following four failure modes represent real-world incident post-mortems collected from high-scale SaaS deployments.

Traditional billing architectures rely on transactional databases (such as PostgreSQL or MySQL) to maintain current usage balance records per tenant. Under high concurrency, executing continuous updates against a shared row triggers catastrophic lock contention.

When thousands of parallel API workers execute this block simultaneously for a single active enterprise key, PostgreSQL worker processes pool in exclusive lock wait states. Connection pools exhaust within seconds, cascading into HTTP 503 errors across application APIs. Chargebee integration layers that rely on synchronous webhook listeners for ledger updates frequently suffer from this bottleneck during batch customer workloads.

Mitigation: Shift from active row updating to append-only log ingestion. Lago avoids row-level locking entirely by treating usage metrics as an append-only stream written directly into ClickHouse storage tables, calculating balance rollups asynchronously via background materialization queries.

Outsourcing meter state to managed external platforms introduces hard dependency risks over external network interfaces. When application clusters emit real-time usage events to Stripe or Chargebee webhooks, downstream rate limits become hard operational ceilings.

Stripe applies strict rate limits across API endpoints (typically 100 requests per second per mode live key, with burst capacity). During unexpected traffic spikes, application clusters attempting synchronous event submission receive HTTP 429 Too Many Requests errors. If application worker retry queues lack proper exponential backoff with jitter, retry storms develop immediately, saturating internal Redis background job queues and crashing memory pools.

While ClickHouse offers incredible event-ingestion capabilities for Lago backends, incorrectly constructed aggregation queries over multi-gigabyte sliding windows can instantly exhaust node memory allocations. Evaluating complex custom metrics like high-cardinality COUNT DISTINCT across 90 days of raw log data forces ClickHouse to allocate massive state maps in RAM.

When a tenant requests an real-time invoice preview, a bad aggregation query triggers an Out-Of-Memory (OOM) kill by the Linux kernel on the primary ClickHouse database node, dropping active cluster queries for all concurrent tenants.

Mitigation: Never run raw aggregate functions over unbounded historical event datasets during live invoice evaluation. Pre-aggregate raw events using AggregatingMergeTree tables paired with background continuous Materialized Views, storing intermediate states in system memory using specialized aggregate state data types (such as AggregateFunction(uniq, String)).

In distributed system topologies, network partitions and microservice retries cause events to arrive out of chronological order. An event generated at 11:59:59 PM on the final day of a billing cycle may arrive at the ingestion pipeline at 00:02:15 AM of the next billing month.

Stripe Billing enforces a default 24-hour window for idempotency keys. If an event is re-submitted past this window due to queue backlog recovery, it risks duplicate billing or permanent rejection depending on timestamp settings. Lago handles this by persisting event primary keys inside high-performance Redis bloom filters paired with persistent ClickHouse unique key constraints, maintaining deterministic deduplication over customizable multi-week operational windows.

Migrating live billing infrastructure while actively processing millions of daily dollars in customer invoices demands zero tolerance for data drift or double-billing. The runbook below outlines an enterprise-tested procedure for transitioning from legacy billing engines to a high-throughput usage metering architecture.

Do not attempt a cold switch of billing systems. Deploy an application-level router that duplicates incoming usage metrics. The primary path routes to your legacy platform, while an asynchronous shadow thread pipes identical payloads to the target engine.

Deploy an automated reconciliation worker that pulls computed period-to-date metrics from both system APIs every hour, asserting financial equality down to the sub-cent level. Highlight and record any variance exceeding 0.0001% for manual audit.

There is no universally superior billing platform. The right platform depends on your transaction throughput, technical complexity, and financial model. Choosing the wrong architecture leads to either unsustainable operational engineering overhead or crushing margin loss from vendor take-rates.

"Architecture is the art of trade-offs. Outsourcing your usage ledger trades infrastructure complexity for linear margin erosion. Building your usage engine on log-structured analytical engines trades upfront engineering effort for infinite scale and total unit-economic control."

Stripe Billing is the ideal choice for early-stage SaaS applications, low-concurrency B2B platforms, and teams without dedicated Site Reliability Engineering resources. If your system processes under 5,000,000 monthly usage events, or if your pricing is driven by simple seat-based tiers with basic overage limits, Stripe eliminates the need to manage databases, invoice rendering logic, or payment gateways. The 0.7% take-rate is a reasonable tax to avoid operating distributed databases during early growth phases.

Chargebee is built for mid-market and enterprise SaaS companies driven by sales-led growth models, complex manual contract modifications, localized international tax rules, and multi-gateway payment processing. If your business requires revenue recognition systems, custom multi-currency invoicing flows, support for legacy ERP integrations, and enterprise sales teams editing contracts in a web UI, Chargebee provides an off-the-shelf management surface that minimizes integration code.

Lago is the required engine for high-throughput API platforms, AI inference services, developer tool providers, and cloud infrastructure vendors where usage metering forms the core product architecture. If your infrastructure generates tens of millions of monthly events, if you require microsecond event ingestion performance, or if vendor platform take-rates threaten your gross margins, self-hosting Lago over ClickHouse and Kafka delivers an resilient, scalable solution. It decouples high event volume from vendor fees, providing complete control over metric calculation and financial state.

Refresh token rotation in Express + TypeScript, explained (with a free boilerplate)

📅 Nov 18, 2026  |  Category: Technology  |  Read Source →

Most Express auth tutorials stop at "sign a JWT, put it in a header, done." That works until you need to log someone out, or until a token leaks. Then you discover a JWT can't be revoked.

In this post I'll walk through the pattern I use instead: short-lived access tokens + rotating refresh tokens with reuse detection. All the code comes from an open-source starter I published, linked at the end.

A JWT is valid until it expires. The server doesn't keep a list of them, which is the whole point: no database lookup per request.

The access token keeps requests fast. The refresh token is the revocable part, so it lives in the database.

Why hash it? Same reason you hash passwords: if your database leaks, the attacker shouldn't get working sessions.

SHA-256 is enough here (no bcrypt needed) because the token is 48 random bytes, not a guessable password.

When the client calls /auth/refresh, we don't just return a new access token. We also revoke the refresh token it used and return a new one.

Every login starts a family (a random id). All tokens rotated from that login share it:

Here's the trick. After rotation, the old token is revoked. A legitimate client never sends a revoked token again, because it already has the new one.

So if a revoked token shows up, someone copied it. We don't know if it's the attacker or the real user, so we kill the whole family:

Both the attacker and the user get logged out of that session. The user logs in again; the attacker can't.

The service only talks to a RefreshTokenRepository interface. In production it's MongoDB; in tests it's a Map. That makes the security tests fast and readable:

The whole suite (17 tests) runs in about a second.

Don't leak which emails exist. Return the same error for "wrong password" and "no such user", and compare against a dummy bcrypt hash when the user doesn't exist so the response time is the same.

Let MongoDB clean up for you. A TTL index on expiresAt deletes expired tokens automatically:

👉 github.com/baivoo28/express-saas-starter

Clone it, set one env var, run npm run dev. If you find something to improve in the auth flow, issues and PRs are welcome. A ⭐ helps other people find it.

10 stocks we like better than Nebius Group ›

The neocloud industry has gotten some bad headlines recently. While not as damaging as some of the headlines surrounding former Nvidia (NVDA -2.37%) CEO Jensen Huang, the secondary effects are harming neocloud stocks like CoreWeave (CRWV -4.30%) and Nebius (NBIS +2.11%). Both of these companies operate in this segment and may have seen the ground shift from underneath them.

But does that warrant the huge sell-off they've experienced? Let's take a look at these two, and see if now is the perfect buying opportunity.

The neocloud business is a fairly new one, and it was brought about by the massive investments in AI infrastructure. Essentially, the biggest AI hyperscalers couldn't get enough computing capacity online fast enough, so other companies decided to form and start building their own AI data centers, then rent those out to the AI hyperscalers. This has been a fast-growing business, as the hyperscalers are basically willing to pay a huge sum of money for access to more computing power.

The biggest problem with this is who is funding these data centers. These upstarts don't generate ample cash flows to build data centers, like some of the other major cloud computing providers. Instead, they must seek outside funding.

This can come from multiple sources, including issuing debt and selling shares in the company. One of the biggest backers of these two was Nvidia, as it saw CoreWeave and Nebius as two of the best operators in this space. Nvidia became a major shareholder of both companies as a result, but that relationship may be coming to an end.

With Huang out as CEO and Colette Kress, who comes from the CFO role, assuming the interim CEO role, these deals may be on hold. CoreWeave and Nebius could lose one of their major financiers and have to turn to the debt markets to raise funds.

That could be an issue, as CoreWeave recently saw some of its debt get priced at "distressed" levels, which means there's a low likelihood of it repaying its commitments. If CoreWeave were to default on its debt, that would leave the neocloud industry with a black eye. Funding would likely dry up for every company involved in this space, as lenders worry about the next firm to go belly-up.

There is huge risk in this industry right now, and the stocks are being priced accordingly. But with high risk comes high potential reward, and these stocks could rebound with a vengeance if the market changes its perception.

Both CoreWeave and Nebius are growing rapidly, but the market really only cares whether these two can pay off their debts and grow sustainably. Because neither of these companies is profitable, judging them on projected sales is the best measure.

CRWV PS Ratio (Forward 1y) data by YCharts

CoreWeave trades for a forward price-to-sales ratio of just 1, while Nebius is a bit more expensive at around 3. The price-to-sales ratio isn't as commonly used as the price-to-earnings ratio because it doesn't account for profit margins, but with these two producing no profits, it's the best tool.

To put it in perspective how cheap these two stocks are, if they could turn a 20% profit margin (which they're a long way from doing), that would price CoreWeave at 5 times forward earnings and Nebius at about 14. Those are cheap price tags for the growth these two are putting up.

But once again, the problem isn't growth; it's whether they can reach profitability. If they can, there's huge upside here. If they can't, then investors should stay away.

I think the market has gotten too bearish on these companies, pricing in virtually no chance of success. If these two can continue with the status quo, they could be due for a huge rebound.

I'm a cautious buyer here, and investors need to keep sizing to a minimum, as the risk is high.
