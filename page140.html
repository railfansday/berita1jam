Why Celery Workers Spawn Zombie Tasks on Hard Termination: The Mechanics of Timeout Propagation

📅 Nov 05, 2026  |  Category: Technology  |  Read Source →

Graceful shutdowns in distributed task execution engines like Celery are notoriously deceptive. On paper, orchestration platforms like Kubernetes dispatch a SIGTERM to the container, the event loop captures the POSIX signal, triggers a cancellation cascade, runs resource cleanup routines, and exits cleanly with status code 0.

In real-world production environments, however, tasks frequently enter an unrecoverable "zombie" state. A worker is terminated, the broker assumes the task is either lost or stuck, and downstream data stores are left holding uncommitted transactions, open socket descriptors, or deadlocks.

This deep dive analyzes the internal mechanics of worker termination, evaluates a complete async shutdown simulation using modern Python tooling (asyncio, Pydantic v2, and orjson), breaks down the failure modes that sabotaged this implementation in testing, and provides the production-grade architectural patterns required to guarantee fault isolation.

Premature optimization that couples code directly to high-throughput C-extensions (orjson) at the expense of environment portability introduces unneeded brittleness. High-throughput data pipelines require orjson, but bootstrapping routines, monitoring hooks, and shutdown orchestrators should always possess self-healing fallback paths to guarantee system observability under hostile runtime conditions.

Codex can call tools from Model Context Protocol (MCP) servers: documentation lookups, browsers, design files, issue trackers and more. You add a server once, and the Codex CLI, the Codex app and the IDE extension all pick it up because they share one configuration. This guide shows the exact codex mcp commands and config.toml keys from the official Codex MCP documentation and the open source Codex CLI, checked in November 2026.

Quick answer: run codex mcp add -- for a local (stdio) server or codex mcp add --url for a remote (Streamable HTTP) server, then start Codex and type /mcp to see the connected servers. Moonshot Just Put a 2.8-Trillion-Parameter Model on Hugging Face — Kimi K3.1 Pro's Open Weights Are Real, and the Fine Print Matters

📅 Nov 05, 2026  |  Category: Technology  |  Read Source →

Posted on Nov 5 • Originally published at convertelementor.com

Originally published on ConvertElementor: https://convertelementor.com/blog/moonshot-just-put-a-2-8-trillion-parameter-model-on-hugging-face-kimi-k3-1-pro-s-open-weights-are-real-and-the-fine-print-matters-november-2026-20261105

Moonshot AI published the full weights of Kimi K3.1 Pro on Hugging Face on November 4, 2026 — 2.8 trillion parameters, a 1-million-token context window, and a license that is genuinely open for most of us but not for everyone.

Moonshot posted the weights on Hugging Face under the repository name moonshotai/Kimi-K3.1-Pro — no access gate, no form, no waitlist. The download is 96 safetensors shards totalling about 1.56 terabytes.

Kimi K3.1 Pro itself is not brand new. Moonshot announced it on October 23, 2026, as the first model in the K3.1 family. What is new is that the full weights are now public.

The headline figure is 2.8 trillion total parameters, which makes K3.1 Pro the largest publicly downloadable model. It is a mixture-of-experts model: it has 896 experts, and only 16 of them activate for any given token, so 104 billion parameters are active at a time.

The context window is 1 million tokens — 1,048,576, to be exact. In 24 of the model's 93 layers, the usual attention mechanism is replaced by a different design, which is part of how it handles that long context.

"Open weights" and "open source" are not the same thing. The weights ship under Moonshot's own Kimi K3.1-Pro License, not a standard open-source license like Apache 2.0. For independent developers, small teams, and most agencies, that licence is permissive enough to use and build on. Read it before you build a product on it, especially at larger scale.

Moonshot's own numbers put K3.1 Pro near the top of the field. On Terminal-Bench 4.0, a coding-agent benchmark, it performed strongly. As with every vendor benchmark table, treat those numbers as a starting point, not proof — they measure what an agent can do, which is the result that matters most for developers.

The download button is the easy part. The weights are about 1.56 TB, and running them locally needs serious GPU hardware. The hosted price is genuinely competitive: $2 per million input tokens and $10 per million output tokens.

The single most useful thing about a model like K3.1 Pro for a WordPress developer is the combination of long context and strong coding ability. A 1-million-token context means a long-context code audit, or a debugging session across a whole theme or plugin codebase, is realistic in one conversation.

The open weights matter for a second reason specific to WordPress: sites that handle client data can, in principle, run capable models on infrastructure they control, rather than sending everything to a hosted API.

First, do not download 1.56 terabytes on a whim. Try it hosted first — on Kimi.ai, through the API, or through a hosted provider.

Second, if you run a WordPress agency, look at the long-context coding angle before anything else. Try it on a real task: a long-context code audit, or a debugging session across a whole theme.

Third, read the license before you build a product on it. For personal use, small teams, and most agencies, the terms are workable — but check them yourself.

Kimi K3.1 Pro's weights release is the rare AI story this week where the headline and the reality line up — with fine print worth reading.

Riskier decisions may offer an early warning of heavier drinking

📅 Nov 05, 2026  |  Category: Health  |  Read Source →

Changes in phone game decisions predicted heavier drinking the following month in a yearlong study of people with alcohol use disorder.

Alcohol has a reputation for making people take risks. But a yearlong study of people with alcohol use disorder found that changes in decision making came before heavier drinking.

When participants took certain risks in phone games, they drank more the following month. Heavier drinking, however, did not predict riskier choices the next month.

The researchers tracked changes within each person rather than simply comparing heavier and lighter drinkers.

Most participants had mild or moderate alcohol use disorder, making them a potentially important group for early intervention.

Hilmar Zech, a postdoctoral researcher at University Hospital Würzburg and TU Dresden in Germany, led the study with Lorenz Deserno.

The team also included co-authors at Charité in Berlin and the Central Institute of Mental Health.

“This temporal direction was specific and was not observed vice versa, even after accounting for the amount of previous drinking,” Deserno said.

The researchers followed 603 people, ages 16 to 65, for one year. All of them met at least two of diagnostic criteria for alcohol use disorder.

In the study, a standard drink held 0.4 ounces (12 grams) of pure alcohol. The participants averaged about three of those a day, and about five on the days they drank.

Every two days, each person reported what they had drunk from a list of 19 options, from a small beer to a bottle of wine.

Every four weeks, they also played four five-minute games on their phones. In one game, fruit fell from a tree and the player tapped to collect it, unless the fruit turned brown.

In another, red circles flashed on a grid and the player had to remember their positions. Those two measured self-control.

The other two measured decision making. In a gambling game, the player chose between a sure amount and a coin flip, in versions built around wins, losses, or both.

In a card game, the player could pay to flip over cards before guessing which of two face-down rows added up to more.

The mixed version offered a possible win or a possible loss on the same flip. In months when a person took that gamble more often, that person drank more the next month.

The card game gave the same result. When someone flipped fewer cards before guessing, they drank more in the month that followed.

In the loss version, the link was reversed. In months when a person gambled more to avoid a sure loss, they drank less the following month.

Earlier studies had compared people with alcohol use disorder with people without it at a single point in time.

Those studies found a similar pattern: people with alcohol use disorder were more willing to gamble when both winning and losing were possible, but less willing when the gamble involved only potential losses.

As far as Zech’s team knows, no study had watched those shifts come and go inside one person and then watched the drinking follow.

“We found that monthly fluctuations in aspects of decision making predicted subsequent alcohol consumption,” Zech said.

Next the team ran the question backward. Did heavy drinking in one month change how a person played the games the next month?

The researchers found no evidence of that pattern.

The forward link also held after the team accounted for the fact that one month’s drinking resembles the last.

In a second analysis built for a year with many zero-drink days, the loss-version result held up, and the other two showed the same direction with more uncertainty.

The two self-control games did not follow that pattern.

A person’s monthly ups and downs in avoiding rotten fruit or remembering circles had no link to the drinking that followed.

Working memory still mattered, but between people instead of within one person.

Participants who could hold more circles in mind drank less on average over the year than participants who could hold fewer.

Cameron Carter, editor-in-chief of the journal that published the study, explained why experimental tasks matter.

“Decision making and cognitive control cannot be accurately examined through interviews or self-reports and instead require experimental tasks,” Carter said.

The effects were small. Zech’s team wrote that they are likely too small to be useful in a clinic yet.

The team had also planned to split the sample in two, with the second half meant to confirm what the first half found.

The pattern was clear in the first half and not in the second, although the two halves did not differ from each other when the team compared them directly.

The team also split the 603 people into random halves 1,000 times. The direction came out the same every time, and a group of about 300 was often too small to detect the effect.

Of the 603 who started, 218 dropped out early. Their data stayed in, and leaving was not tied to how they played or how much they drank.

The self-control games may simply have been played too rarely. A few studies that checked several times a day did find self-control dipping before drinking, though only under certain conditions.

Once a month may be too rare to catch that. And a study that watches people without changing anything can’t say that the risky choices caused the drinking.

Whether a game score can predict heavier drinking over the following week, rather than month, is still an open question.

The team envisions an app that flags changes in a person’s risk-taking score and offers automated support or prompts them to seek help in person.

Whether that approach would work remains untested.

The full study was published in the journal Biological Psychiatry: Cognitive Neuroscience and Neuroimaging.

Grimes has been on the cutting edge of the overlap between artificial intelligence and music, and now, she’s doing the same with the technology and film.

As revealed Thursday (Nov. 5), the alternative singer-songwriter is part of the cast of Gods Don’t Give Gifts, the first AI-generated movie coming to theaters. The announcement is fitting, considering Grimes has long been interested in the ways the controversial technology is developing. She’s now gearing up to release her new album, Psy Opera, which explores the complexities of AI and uses artificially generated music on one of the tracks.

GM Patents Launch Control That Watches the Drag Strip Christmas Tree, Launches for You

📅 Nov 05, 2026  |  Category: Technology  |  Read Source →

The recent patent describes a system that manages the brakes and throttle to deliver remarkably consistent drag strip blasts away from the line.

Getting a great launch at the drag strip takes more than horsepower and sticky tires. Drivers also need to time their start perfectly; even a tenth of a second can make a difference. Now, General Motors has patented technology that could take that last bit of human involvement out of the equation entirely.

The system uses the vehicle's cameras to watch the drag strip's Christmas Tree, predict when the light will turn green, and launch the car automatically. Better yet, it can actually begin preparing the launch before the green light illuminates. We might be about to see the age of push-button drag racing.

The technology is detailed in U.S. Patent 12,780,203, titled “Methods and Systems for Coordinating Launch Control for Vehicles for Racing.” Originally filed in January 2025, the application was published in July 2026 before finally receiving its patent grant on November 3.

At its core, the system builds on the launch control technology already available in modern performance cars. Right now, most launch control systems work very similarly: the driver applies full brakes and full throttle, and holds both pedals until it's time to go; they let off the brake, and the car rockets away. GM's proposed technology takes over most of that process.

The craziest bit is just how it manages all of this. First, it uses on-board cameras to identify the Christmas tree at the drag strip. Once it recognizes the lights, it notifies the driver and prompts them to activate launch control. Those who want to try this new method could control it much the same as they do with existing systems; the patent describes drivers putting their feet on both pedals and then, once the automatic launch system takes over, the driver can remove both feet and let the car work.

The car can maintain braking pressure and staging torque automatically, even after the driver releases the pedals. The clever part comes next: rather than simply waiting for the green light, the software identifies the sequence of yellow lights and compares it against stored timing patterns to calculate precisely when the race will begin.

That's key, because different events run the lights at different times. For example, a Pro Tree illuminates all three amber lights simultaneously before turning green 0.4 seconds later, whereas Sportsman Tree illuminates the amber lights sequentially with half-second intervals. GM's system could account for those differences automatically. The system is even capable of calculating the delay between commanding movement from the vehicle and the vehicle actually moving forward.

That all said, this is just a patent for now. GM doesn't mention any specific vehicle or plan for production in its filing. If it does bring it to market, we'd be eager to see how close it can come to cutting a perfect light.
