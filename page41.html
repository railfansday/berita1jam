Accelerating development for massive Git repositories

📅 Nov 17, 2026  |  Category: Technology  |  Read Source →

Android’s source code is big – the Android 17 open source release has 1,084 Git repositories, 1.62 million files, and takes 300 GB for a built workspace. Additionally, in a typical Android source tree with hardware vendor code and first-party applications, the size increases by 2-3x. Traditionally, it took over 30 minutes to fetch Android Open Source Project (AOSP) source code and well over an hour to build on even highly capable developer workstations. As software development evolved over the last 2 years, modern coding harnesses and LLMs have accelerated the development of many projects. These tools are used today for Android operating system development, but the long sync and build times make them less efficient. Both human developers and agents need quick setup, parallel workspaces, and fast build-and-test iteration times.

We built Another Build File Service (ABFS) to address these bottlenecks. ABFS is a full suite of software across a Linux kernel filesystem module, user-space daemons, and server-side infrastructure. ABFS uses content-addressability across the entire stack to lazy-load and cache source code, developer workspaces, intermediate build files, and build results.

Today, we are excited to announce that ABFS is open source on GitHub.The impact of ABFS to Android is:

ABFS already powers parallel workflows for developers and agents in Android, but it is designed to scale to other massive Git-based projects.

In the Android build system, developers define build rules in Blueprint files (Android.bp), Soong compiles them into Ninja files, and Ninja executes the final build graph (see the Android build overview). Similar to the Make build tool, Ninja is timestamp-based. If a build step’s input file is newer than the existing output file, Ninja rebuilds the output file.

Analyzing the AOSP code for Android 17 shows the sheer disk footprint and file count involved in a single checkout and build.

In a typical Android tree that includes hardware-specific repositories, board support packages, first-party applications, form-factor-specific code, etc., the code size is 2–3 times the size of AOSP (over 3,000 Git repositories), compounded across multiple active SKU and legacy maintenance branches.

Building the Cuttlefish emulator target executes a build graph with 192,249 Ninja actions. While local incremental builds are fast once a tree is already built, every new workspace, branch switch, or ephemeral agent session starts cold.Even though typical developer changes touch only 1-10 different Git projects, someone building locally without any remote execution might waste up to 80 minutes on a 64-core machine repeating work their CI system already built. Even if a developer edits a core library like system/libbase, 97% of the build graph is identical to the CI build.

Sharing cached build outputs across CI and local machines is also tricky in a codebase of Android's age and rate of change. Build rules occasionally introduce hidden dependencies (such as passing an undeclared schema file inside raw compiler flags), over-declared inputs, or undeclared outputs. In timestamp-based builds, hidden dependencies silently produce stale incremental artifacts, forcing developers to wipe output directories and run clean builds.

ABFS makes building Android fast by replacing massive local source checkouts with a virtual, content-addressable filesystem (CASFS). ABFS streams files on demand only when a build actually touches them and utilizes shared build caching to help eliminate redundant downloads and compilation.

On the server side, Git-pushers continuously ingest new Git objects from Gerrit or other Git hosts into a horizontally scalable gRPC ABFS Content-Addressable Storage (CAS) Server that indexes Git content, workspace snapshots, and build step results. On the developer host, a local Least Recently Used (LRU) Cacheman daemon, Mount Daemon, and Tap utility connect user-space build tools to the kernel filesystem so checkouts and builds stream only what they need. See the full ABFS architecture on GitHub.

At the core of the client is a virtual filesystem called Content-Addressable Storage Filesystem (CASFS), a Linux kernel module that exposes Git SHA content hashes via extended attributes. When a file's hash is set, CASFS populates its metadata immediately and downloads file bytes via Cacheman only when needed:

Initial checkouts download only lightweight directory metadata prepopulated with Git hashes. CASFS uses Git's object model natively, allowing standard git and repo operations to work transparently.

CASFS can also tap build processes. Tapping records every file actually read, written, or deleted into lists called patches, which are stored alongside cached build outputs. Ninja-go replaces timestamp checks with two-phase content-addressable caching:

Ninja-go accelerates Ninja-based builds like Android and Chrome; other build systems can integrate with ABFS's caching APIs using the same model (see the two-phase caching walkthrough on GitHub).

Each mounted checkout attaches to a persistent workspace that eagerly syncs modified files, git state, and repo state through Cacheman to the ABFS CAS Server—keeping mounts synchronized across sessions or across multiple developer hosts.

Because ABFS does lazy loading and local cache deduplication, developers and their agents can now mount multiple concurrent Android workspaces on a single machine, benefit from a shared local build cache, and achieve massive scale in development time.

An agent can check out a full Android tree in under 10 seconds and perform a full build in under 10 minutes. Agent swarms are empowered to iterate, review, and test in parallel, which can lead to higher quality solutions and speed.In the demo below, an agent makes a system/libbase fix on the latest AOSP release, then 4 parallel agents simultaneously backport, build, and test the fix across 4 more AOSP releases on a single VM.

We released ABFS as open source because we want developers, Android partners, and any large-scale Git-based project to benefit from what we have learned and be able to scale.

While Android’s Soong/Ninja pipeline was the first acceleration target, ABFS was built to be extensible to other build systems. Content-addressable build systems like Bazel map naturally onto CASFS and there is already a proof-of-concept integration with Bazel. Chromium, the Android Common Kernel, and other Google projects are exploring ABFS compatibility.

How You Can Use an Upper-Lower Workout Split for More Gains

📅 Nov 17, 2026  |  Category: Technology  |  Read Source →

If you want to build strength and muscle, split your workout plan in two.

THE STRUCTURE OF your workout over the course of weeks and months should depend on more than just the latest fitness fad. When you’re working toward a goal—whether that’s tied to building muscle, forging strength, losing weight, or improving performance—you’ll have the most success if you follow a plan. That plan (often called a workout split) should take into account arange of factors, including your specific goals, your experience level, schedule, and available equipment.

And one of the most well-known (and easy-to-understand) approaches to this is the Upper-Lower split, which is one of several workout splits organized around training different parts of the body on different days.

An Upper-Lower Split program is broken down exactly as its name implies. One day you’ll train the muscle groups in your upper body (think chest, shoulders, back, arms); then the next you’ll train your lower body muscles (quads, glutes, hamstrings, calves). In general, that means your upper body gets to recover on days you’re training your lower body, and vice versa.

This approach is one of a handful of training splits that works very well if you’re trying to add muscle, or if you’re somebody who’s chasing body recomposition. If you’re trying to build muscle, the more frequently you can train a muscle group with effective, hard sets, the better.

And an upper-lower split lets you train each muscle group at least twice a week, with solid rest in between each session. You’re training each muscle group more frequently than you would if you were doing a bro split (training just one body part a day). And you’re able to do more sets and exercises for key muscle groups than you would if you were doing a full-body training split.

Reading car fault codes from a web page: Web Serial and Web Bluetooth vs. cheap ELM327 clones

📅 Nov 17, 2026  |  Category: Technology  |  Read Source →

A cheap ELM327 adapter, Chrome, and two browser APIs are enough to read engine fault codes without installing anything. The protocol part is small; most of the code deals with how real adapters and real browsers misbehave, and that part is what this post covers.

Disclosure: I built diagnost.net, and everything below comes from its client-side code (elm.js, obd.js, kline.js). It is served to every visitor, so you can check any snippet against the live page at https://diagnost.net/connect. The code comments are in Russian; I paraphrase them here.

Platforms: Windows, macOS, Linux, Android. Safari and Firefox don't expose these APIs. On iPhone, no browser can reach either Bluetooth or USB, because the restriction is in iOS itself, so Chrome on iOS is in the same position as Safari.

The page has two transports: elm.js talks to an ELM327 over USB or BLE, and kline.js talks to the car directly over K-line through a dumb USB cable (more on that later). Both expose the same function:

Frames come back already stripped of headers and checksums. The OBD-II layer (obd.js) — reading stored codes (mode 03), pending codes (07), freeze frame (02), sensors (01), VIN (09), clearing codes (04) — is written once and doesn't know what sits under it. If you build anything on top of serial hardware, this split is worth copying: all of the hardware-specific pain stays below one interface.

navigator.serial.requestPort() only opens if it's called during a user activation. That sounds trivial until you do async work first. The page probes the adapter at several baud rates, which can take a while, and if it then decides to show the picker, the gesture has expired and you get a SecurityError.

First, when the user clicks "pick another adapter", the picker is requested synchronously, before awaiting anything. Second, if the page discovers late that it needs a picker, it doesn't try to open one; it shows a button, and that new click provides a fresh gesture.

For repeat visits the page calls navigator.serial.getPorts() and opens previously granted ports without asking again. If that list is empty, getPorts() returns quickly enough that requestPort() is still inside the same gesture.

Also note: in Firefox and other browsers with a stubbed implementation, navigator.serial may exist while the picker throws NotSupportedError. Feature-detecting the object isn't enough; handle that error as "not supported".

This one costs time if you don't know it. port.open({ baudRate }) resolves at any speed, because the USB-serial driver doesn't check it. ELM327 clones differ: most cheap ones run at 38400, firmware 1.5+ and OBDLink at 115200, very old ones at 9600. The only reliable test is to send ATZ and wait for the > prompt.

heard tracks whether anything at all arrived from the port. "Silence" and "something answered, but not an ELM" lead to different messages for the user.

Reading is a plain pump loop on port.readable.getReader(), decoding with TextDecoder and feeding a buffer. One detail matters: everything in the buffer before a new command starts is discarded. Otherwise a late tail from the previous attempt (for example, garbage from the wrong baud rate) gets attributed to the next command, and every response after that is off by one.

If a write is still pending, the writer stays locked, releaseLock() doesn't free the stream, port.close() rejects, and the next connection attempt hits the same port as "busy". The close sequence that works:

Every step has a time cap, because waiting for a flush that never comes is how tabs hang. A failure of port.close() itself is not hidden: the promise rejects, since the port may still be open. The page also releases the port on pagehide.

The DOMException name is the main signal you get, and some names are ambiguous:

The last row matters for UX. Telling the user "close the other program" on NetworkError would be wrong whenever the cable had simply been pulled, so the page only says "busy" when that's proven (InvalidStateError) and shows a neutral "couldn't open the port" otherwise.

Every ELM327 BLE clone hides its serial channel behind a vendor service. Web Bluetooth only lets you access services you listed up front, so the list doubles as optionalServices — without it getPrimaryServices() returns nothing:

After connecting, the page walks the services (known ELM services first, so it doesn't latch onto some unrelated pair) and picks the first characteristic with notify/indicate plus the first with write/writeWithoutResponse. It writes with writeValueWithResponse if the characteristic supports write, otherwise writeValueWithoutResponse.

If the adapter is paired with the operating system, the browser won't see it in the picker. Users have to remove the pairing first.

Some cheap BLE clones advertise a service that never returns its characteristics (on KONNWEI adapters it's 180A, Device Information). Chrome walks every service on the device, gets stuck on the broken one, and the getPrimaryServices() promise never settles — no resolve, no reject. Without a guard the page showed "Connecting to the car…" forever.

A BtStage error gets its own message: the adapter responded but didn't give the browser its service list, so try USB or another adapter.

Once a stage times out, the underlying gatt.connect() may still resolve later. And for the same adapter, the browser hands back the same BluetoothDevice and the same GATT server object. If the user retried in the meantime, a late disconnect() from the old attempt would kill the new session. The page stores the owner of each GATT server in a WeakMap keyed by device.gatt, and only the latest attempt is allowed to disconnect.

The opposite also needs handling: on every failure after connect(), the page has to call gatt.disconnect() explicitly. Otherwise the tab keeps holding the adapter, and the next attempt, from this page or from another program, can't get it.

ELM327 speaks text: send 0100\r, receive lines, and a > means "ready for the next command". Sounds like a simple request/response queue. On BLE it isn't, because the notification with the answer can arrive before the writeValue promise resolves. The first version treated > as "done" and sent the next command while the previous write was still in flight. Chrome replied with GATT operation already in progress.

The fix is to queue whole transactions and treat a command as finished only when both events have happened:

The same queue serves both Web Serial (writer.write) and Web Bluetooth (writeValue*), so USB gets the same guarantee for free.

The true passed to fin() on timeout or write failure is the other half. After a timeout you don't know whether the command reached the adapter or whether its answer is still coming; on BLE the write may still be sitting in the stack. If you send the next command, it may receive the previous answer. So the link is marked failed: the active command and the whole queue are rejected with LinkFailed, new send() calls reject immediately, and nothing more is written. Only a new connection recovers. The UI catches LinkFailed, stops live polling, and says the connection was lost. I prefer that to "wait for silence and continue", which gives you data shifted by one response.

Timeouts: 8 s per command, 12 s for long OBD requests, and 30 s for the first 0100, because after ATSP0 the adapter cycles through protocols and that can take up to about 20 s. If the AT commands passed but 0100 timed out, the adapter is alive and the car is silent (ignition off, usually), and the user is told exactly that.

The response parser splits into lines first, drops status words (SEARCHING..., NO DATA, ERROR, ...), and only then converts hex. On K-line each ECU answers on its own line; on CAN a long response arrives as 0:, 1:, ... chunks preceded by a length line. An early version glued lines together, and on a real BMW E46 the genuine codes P0313, P0171 and P0174 came out as P1301, C3101 and C3443. Wrong parsing here doesn't crash; it produces believable, non-existent fault codes.

Each code is two bytes: the top two bits pick the letter (P, C, B, U), the rest are digits. On CAN there's also a count byte right after the service ID, so the protocol number from ATDPN decides the offset. The page then fetches short descriptions for the found codes and links each one to its own page, like https://diagnost.net/codes/P0420.

One more rule: if the car answered nothing at all, the code list is "not read", not "no faults". A green "all clear" on a silent ECU would be false.

Some users plug in a BMW K+DCAN cable instead of an ELM327. It's a transparent USB↔K-line adapter: no AT commands, and since K-line is half-duplex, the cable echoes back every byte you send. ATZ comes back as ATZ at every baud rate. That echo is how the page recognizes the cable.

Web Serial turns out to be enough to drive K-line directly: it supports 10400 baud, and port.setSignals({ break: true }) pulls the line low. ISO 9141-2 starts with the ECU address 0x33 sent at 5 bits per second — 200 ms per bit — using break as the zero level:

setTimeout drifts by milliseconds, so the code sleeps until 8 ms before the mark and spins the rest. Per the measurement in the code comments, setSignals costs about 0.3 ms and the spin keeps precision under 1 ms.

ISO 9141-2 via 5-baud init was verified on a real E46. The KWP2000 fast-init path exists but hasn't been tested on a car yet. All of this only applies to K-line cars, roughly pre-2007; D-CAN over a browser serial port isn't possible.

Web Serial and Web Bluetooth are usable for real hardware today, in Chromium browsers. Budget most of your time for the edges: which errors are ambiguous, which promises never settle, and which events arrive out of order. One design decision I would repeat: making error types specific — "adapter silent", "car silent", "not an ELM", "port held by this page" — because each one tells the user to do something different.

In case you, for some reason, don’t want to use the nearly identical Apple Wallet.

It's an odd integration considering Apple has its own Wallet app that's very similar to Google's offering. Both can handle digital payment tools, they store tickets and travel information and they safely store IDs and credentials.

OpenBot: How to Run a Team of AI Agents on Your Computer

📅 Nov 17, 2026  |  Category: Technology  |  Read Source →

Posted on Nov 17 • Originally published at blense.tech

Everyone has been part of a school group project where each member wrote their section alone at home without talking to anyone else. The night before the deadline, someone pasted everything into a single document. The result was an academic Frankenstein: the introduction ignored the conclusion, every section cited sources differently, and arguments contradicted each other right on the page.

Despite rapid progress in language models, most of our day-to-day work with AI still repeats that exact dynamic. We open a chat window, ask a question, copy the response, and close the tab. The next second, all project context and reasoning vanish.

It feels like hiring a brilliant freelancer with severe amnesia: they have to relearn your entire business from scratch before every single task.

For one-off questions, that transactional relationship works fine. For ongoing workflows—code maintenance, product launches, support triage, or operational monitoring—the real leverage comes from accumulating context over weeks. That is the shift OpenBot, a source-available project by Synthetify Labs, puts into practice by replacing the disposable chatbot with a resident operational team right on your computer.

OpenBot's core difference isn't launching yet another proprietary model. The desktop app is built on a local-first architecture and follows a Bring Your Own Plan model: instead of charging token markups, it connects to the AI subscriptions and API keys you already pay for—or to local model servers running on your own hardware.

Rather than relying on ephemeral cloud threads, every team member gets a continuous technical environment on your machine built on four pillars:

In practice, the source-available codebase in nightly-labs/openbot (under the PolyForm Noncommercial 1.0.0 license, free for personal use on macOS, Windows, and Linux, with remote access via web, iOS, and Android) turns AI from an isolated utility into a permanent deskmate.

With context preserved on disk, agents no longer live in solitary tabs—they coexist in shared channels, much like a #launch room, except populated by humans and models from different vendors working side by side.

In the same thread, an agent backed by Codex can investigate a bug, another on Claude Code writes tests or reviews the patch, while a third on Gemini or Grok organizes release notes. The ecosystem also supports OpenCode (including free models with no account required), Cursor, Cline, Muse Code, Pi, Inception's Mercury models, any agent compatible with the Agent Client Protocol (ACP)—such as Goose, Qwen Code, and GitHub Copilot CLI—and 100% local models via Ollama and LM Studio.

Working together in a persistent space unlocks a decisive shift: strict specialization. Instead of a generic assistant doing everything adequately, the official OpenBot Marketplace catalog features 27 agents with narrow scopes and explicit boundaries:

Putting brilliant specialists in the same room creates an obvious risk: without a protocol, everyone talks and edits files at the same time.

To prevent collisions, OpenBot channels run on crash-safe FIFO message queues (First In, First Out) with strict state control. At any given moment, there is only a single task owner.

A real workflow shows how this engine turns without human micromanagement:

An assistant that only acts when you type a command still demands constant mental overhead to remember, prompt, and follow up. To remove that friction, OpenBot attaches scheduled routines directly to resident agents.

Think of them as classic cron jobs, except they wake up the full language model with access to local context, accumulated history, and authenticated browser tabs. Chief of Staff wakes on weekday mornings to cross-check your calendar, emails, and commitments and post a ~25-line briefing before your workday starts. QA Tester runs morning smoke checks against production, while Ops Digest sweeps Notion, Airtable, or Trello boards on Friday afternoons to flag overdue items.

Yet the most mature engineering detail in this architecture is the silence rule, implemented through the routine_no_update function. In immature automations, if nothing broke overnight, the bot still sends a cheerful message saying everything looks fine—flooding your phone with operational noise.

A well-designed routine works like a smart alarm clock: it wakes up on its own, reads your emails, checks your flight status, and only wakes you up if boarding has been canceled.

When an agent runs its routine in OpenBot and finds no anomalies or relevant updates, its instructions tell it to call routine_no_update. The channel stays completely silent, protecting human focus.

Giving background agents access to local directories, a terminal, and an authenticated browser raises an inevitable security question. OpenBot's technical documentation is candid about this: after initial consent, local agents run with danger-full-access permissions and approvalPolicy: never inside the local environment.
