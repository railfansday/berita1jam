Efficient GDAL Workflows: Reading Zipped Archives In-Place

📅 Nov 25, 2026  |  Category: Technology  |  Read Source →

Posted on Nov 25 • Originally published at u11d.com

Geodata rarely arrives as a single file. A Shapefile is at least three files (.shp, .shx, .dbf) and usually a .prj, so users, survey contractors, and public data portals zip them. Your upload endpoint receives a .zip, hands it to GDAL, and gets this:

That is GDAL 3.13. Earlier versions print only the first sentence, without the hint, and before 3.10 it reads "not recognized as a supported file format". Called from code, the same failure can return None with an empty error message. Even with the fix GDAL suggests, some valid archives still refuse to open, and a path that works on your laptop fails once the service runs from a different working directory.

The short answer: prefix the path with /vsizip/, as in /vsizip/roads.zip. GDAL then reads the archive in place, from disk, memory, or object storage, without extracting anything. The rest of this guide covers doing that safely in an upload handler, using the Python bindings: reading uploads from disk or memory, validating what is inside, the archive layouts that still fail, and how to get a useful error when they do.

GDAL drivers read files; they do not unpack archives. /vsizip/ is a virtual file system, not a driver: prefix a path with it and GDAL presents the contents of the zip as a directory. The driver that opens the data (Shapefile, GeoJSON, GeoPackage) never knows an archive was involved.

The same path works anywhere GDAL accepts a data source, including ogr2ogr. This converts one layer of a zipped upload straight to GeoPackage:

If you control the file name, there is a shortcut. Since GDAL 3.1, the Shapefile driver opens an archive named *.shp.zip (one or several layers) or *.shz (a single layer) directly, with no prefix:

This only helps for Shapefiles, and only when the extension is exactly .shp.zip or .shz. For uploads, where the user picks the name, use /vsizip/ explicitly.

If the upload already has a path, use it. A file saved by an earlier step, an object in S3 (Step 6), or a Django upload larger than FILE_UPLOAD_MAX_MEMORY_SIZE (2.5 MB by default), which arrives as a TemporaryUploadedFile with temporary_file_path(), can go straight to /vsizip/. GDAL then reads only the parts of the archive it needs, where the file already is. Reading the file into Python first, only to hand GDAL a copy, loads the whole archive into memory for nothing.

Some uploads have no path. Smaller Django uploads stay in memory as an InMemoryUploadedFile; Flask and FastAPI keep small uploads in memory and spool larger ones to anonymous temporary files, and give you a file object either way; a message queue or an HTTP client gives you bytes. For those, /vsimem/ is GDAL's in-memory file system: register the bytes under a path, then chain /vsizip/ on top of it.

The double slash in /vsizip//vsimem/… is not a typo: it is /vsizip/ followed by the absolute path /vsimem/…. The same holds for a file on disk: /vsizip/ followed by /srv/uploads/roads.zip is /vsizip//srv/uploads/roads.zip.

The zip holds more than one member, so GDAL presents it as a directory, and the driver that matches the file inside does not accept one. How to Isolate AI Coding Agents With Docker Sandboxes v0.54.0 and AI Governance

📅 Nov 25, 2026  |  Category: Technology  |  Read Source →

Posted on Nov 25 • Originally published at mangodeveloper.com

Running an autonomous coding agent like Claude Code, Cursor, Codex, or Kiro directly on your host workstation gives that agent the same filesystem, network, and credential reach as your own user account. A single prompt injection buried inside an untrusted repository, dependency script, or issue thread can read ~/.ssh, exfiltrate environment variables, or invoke destructive Model Context Protocol (MCP) tools before you notice a terminal command ran.

Standard containers were built to isolate predictable application workloads, whereas AI agents act as autonomous operators that decide what code to write, which packages to pull, and which external endpoints to query. In mid-November 2026, Docker shipped Docker Sandboxes v0.54.0 alongside its Docker AI Governance architecture, wrapping each coding agent inside a dedicated microVM with enforceable network proxies, mount policies, Cedar-based MCP tool rules, and structured SIEM audit logs.

This guide walks through setting up Docker Sandboxes v0.54.0 from scratch, locking down outbound network traffic with a default-deny baseline, building reusable sandbox templates via snapshots and Dockerfiles, enforcing Cedar policies across the MCP Gateway, and migrating past the breaking SSH and Git transport changes introduced in the November 2026 releases. All commands, settings keys, and policy syntax below are drawn from the official Docker Sandboxes release notes, Docker AI Governance documentation, and Mohammad-Ali A'rabi's v0.51+ toolchain walkthrough.

A standard docker run container shares the host Linux kernel (or the shared Linux VM kernel inside Docker Desktop on macOS and Windows). If you grant an agent inside a regular container access to /var/run/docker.sock so it can build and test container images, that agent effectively gains root-equivalent control over the host Docker daemon.

Docker Sandboxes solves that architectural problem by giving each sandbox its own lightweight microVM managed by the sbx CLI and background sandboxd daemon. Every sandbox runs an isolated kernel, a private internal Docker Engine, a dedicated filesystem boundary, and a host-enforced network proxy.

plaintext sbx settings set mcp.useServerNamePrefixes true

rego permit (principal, action == MCP::Action::"invokeTool", resource) when { resource in MCP::Server::"internal-tracker" && resource.readOnly == true };

Opaque Sessions Versus JWTs for Revocable Web App Access After Phone Login

📅 Nov 25, 2026  |  Category: Technology  |  Read Source →

A successful phone code should not buy an abusive shopper access that the store cannot withdraw. For a web app choosing an opaque session versus a JWT, revocation is the operational constraint that determines my default when adding phone one-time-code login.

Short answer: use opaque sessions for the browser when incident response requires immediate revocation, and budget for a session lookup on authenticated requests. JWTs allow offline verification, but a valid token ordinarily remains usable until expiry unless the verifier consults additional revocation state. Sessions at the edge and short-lived JWTs internally can be a reasonable compromise.

Consider a production-response rehearsal, not a report of an actual incident: I am reviewing the launch plan, phone verification succeeds, and an automated client begins using its new session to reach account and checkout functions. The responder revokes that session. The next authorization decision is the test. If a verifier accepts the old credential because its signature and expiration still check out, the phone login worked while containment failed.

The invariant is narrower than preventing every bot: after the authoritative session record is revoked, subsequent authorization checks must reject it. Requests already authorized are a separate boundary. An application shouldn't promise that deleting a session rolls back a purchase that has already committed.

Phone verification establishes that someone could complete that challenge; it doesn't settle whether the resulting activity should continue. For this rollout, I would review code-request abuse, verification attempts, and authenticated activity as separate control points, because stopping a session doesn't stop a client from requesting another code, while throttling code delivery doesn't invalidate an existing credential. The session decision belongs inside that larger abuse plan.

An opaque identifier makes the server's record authoritative.

The credential alone doesn't tell the application whether access is still allowed, so the application asks the session store, checks expiration and revocation, and only then proceeds. That lookup is the mechanism behind immediate revocation, not incidental overhead to optimize away during the first traffic spike.

A JWT shifts part of that decision into the credential. A verifier can validate its signature and claims without asking the issuer about each request. The operational catch is straightforward: a signature proves that a token was issued, not that the issuer still wants it accepted. Expiration bounds that exposure; it doesn't make the exposure disappear.

A revocation list or a current-account-state lookup can change the result. It also changes the capacity plan, because a supposedly offline path now depends on shared state.

Revoking a refresh token shouldn't be described as instantly invalidating every already-issued access token. Those are different credentials with different acceptance rules.

For a planning example, assume 400 authenticated requests per second during normal shopping and a threefold promotion surge. With one session lookup per request, the surge requires 1,200 lookups per second before retries, operational headroom, or any additional account checks. These are illustrative workload assumptions, not measured throughput or a vendor benchmark. Replace them with the existing application's traffic distribution before choosing storage capacity.

The phone-code send rate is a poor proxy for session-store demand: one successful login can lead to many authenticated requests, and abusive traffic can keep presenting a credential long after the login flow ends. The store therefore needs its own latency budget and saturation signals. An authentication SLO should count a legitimate shopper's ability to complete an authorized request, while a separate containment objective tracks how quickly revocation reaches every verifier. Combining those into one success percentage can conceal a security failure behind good availability.

Caching deserves particular skepticism. If a verifier caches an accepted session for 30 seconds without checking invalidation, that deployment has accepted a potential 30-second revocation delay. Calling the underlying record immediately revocable doesn't repair the application-level promise. Either preserve authoritative checks, establish an invalidation mechanism with a defensible bound, or document the weaker containment objective.

The dependency also has a failure policy. For protected operations, a lookup that cannot establish validity should deny access; treating an unavailable store as permission to proceed defeats the reason for selecting opaque sessions. That policy can affect availability during a storage incident. Budget and test for it.

A product's ability to issue credentials is only the beginning of the comparison. The review question is what the existing app will consult before allowing an abusive account to act again, and who owns that dependency during an incident. The following are selection boundaries, not claims that any product automatically satisfies a particular SLO.

Infrai offers one key, one bill and one REST API for 295 routes across 20 modules: a broad capability surface with a simple consistent interface. A managed service reduces the infrastructure the platform team operates but introduces an external dependency and a contract that application code must follow. Self-hosting gives the team more operational control while making recovery and upgrades its responsibility. Neither arrangement removes the need to prove that every protected path respects revoked access.

The opaque-session default does not apply when a verifier genuinely cannot call back and can tolerate access remaining valid until expiry. JWTs fit that constraint. The decision should name the accepted exposure window and the service that owns it, rather than treating statelessness as a universal performance requirement.

Sessions at the browser edge with JWTs internally are a legitimate middle ground, provided the internal token's remaining lifetime is included in the containment promise. Revoking the browser session prevents subsequent issuance through that session; it does not retract an internal credential already issued to a verifier that checks only its signature and expiry.

Not since my first viewing of that film 25 years ago had I felt that sense of being dwarfed by mythology, and to re-experience it in Berlin’s famous nightclub Berghain of all places was a delight.

Ala Roushan and Charles Stankievech, an artist duo hailing from Iran and Canada, respectively, expertly blended archaeology, artificial intelligence (AI), acoustics, chemistry and sculpture to create a profoundly multi-sensory experience in A Shroud of Woven Solar Threads earlier this autumn (2-18 October).

Ala Roushan and Charles Stankievech, Sūryasya Śántau (Within the Solar Silence), 2026. Halle am Berghain Courtesy of HOUSE in partnership with Autotelic Foundation. Photo: Noshe

Situated inside Halle am Berghain—a gargantuan former power station that, yes, was reminiscent of J.R.R. Tolkien’s Khazad-dûm—the installation was presented by the Berlin-based contemporary art initiative House, helmed by Juliet Kothe, who co-curated with Nadim Samman. The exhibition was co-presented by the Autotelic Foundation, whose whimsical take on AI art in Venice had been one of the standout digital presentations during the most recent Biennale.

At the centre of A Shroud of Woven Solar Threads was a towering, eight-minute-long, 4K video installation that slowly panned through a digitally rendered, 4,000-year-old Mithraic cave temple, created based on 3D scans of the ancient site. Originally made for an exhibition in Lausanne in 2025, the installation was expanded to take advantage of the Halle am Berghain’s size.

Each speaker featured a different voice, all chanting in an AI-generated, speculative Proto-Indo-Iranian (PII). PII is the ancestor of the Indo-Aryan and Iranian language families, including Sanskrit and Avestan. There are no historic documents or written texts in PII, let alone documented Mithraic chants from that period.

Together they drew on comparative linguistics to reconstruct plausible linguistic forms, and AI allowed them to bring the speculative language to life. One of the speakers, Roushan said, was based on her own mother’s voice, which had been used to train one of the AI chanters.

"Mithra…" the chant began, referring to the ancient solar deity, a kind of lesser-known Ra, and as the incense burning in the hall filled one’s nostrils it was difficult not to feel transported by the sheer scale and the acoustic prowess of the installation.
