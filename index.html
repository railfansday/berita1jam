Fast, reliable A2UI, with swappable inference formats

📅 Nov 03, 2026  |  Category: Technology  |  Read Source →

We've heard your concerns about the speed of A2UI and generative UI experiences: people wait while the model generates each screen. This release gives you levers to make that faster, so you can choose the trade-off that fits each screen.

With this release, we’re happy to introduce swappable inference formats and share examples on leveraging decision models with A2UI, which help building faster and more reliable generative UI experiences. Using our new A2UI Express as an inference format you can reduce latency by up to 3x, and up-to 80x using decision models like Jev to make layout decisions. Express requires up to 3x fewer tokens to generate the same kinds of UI compared to Direct JSON. We'll dive into the details in this blog post.

A2UI is an agent-optimized protocol for generative UI, where a client advertises a catalog of trusted components as a contract, an agent sends A2UI messages describing a bespoke user interface composed from that catalog, and the client's renderer draws the UI (see Introducing A2UI).

Initially agents generated A2UI JSON transport messages directly, every curly brace and nested element. It turns out that generating JSON trees constrained by a complex JSON schema is slow and error-prone for LLMs. This coupled A2UI to LLMs, which output text, and made it difficult to integrate faster System One decision models.

Now agents can generate A2UI Express, an intermediate format optimized for inference speed and accuracy, and rely on deterministic code in A2UI's Agent SDKs to translate it into the JSON-based transport protocol. Agent builders are also free to swap in any other DSL and its associated compiler for any special use-cases, and our A2UI Agent SDK(s) make it compatible with transports and renders.

The format the model generates is what we call inference_format. You set it with one argument when you create the generator. The SDK generates the prompt instructions for that format and compiles the model's reply into standard A2UI messages. This post covers how the swap works, why we developed A2UI Express as the new default inference format, and how a decision model can build screens from layouts you define in advance.

An inference format has two parts, and the SDK generates both from your catalog's JSON schema. A prompt section teaches the model the format's syntax, and a compiler compiles the model's reply into validated A2UI messages. Because both come from the schema, a format can't describe a component or property that your catalog lacks.

A2UI Express is available in the Python agent SDK (a2ui-agent-sdk 0.9.0 on PyPI), in the TypeScript agent SDK (@a2ui/agent on npm), and in the Dart SDK (a2ui_agent 0.0.1-wip004 on pub.dev). In TypeScript, you pass new ExpressFormatFactory() as the generator's third argument. The Python and TypeScript SDKs can both stream Direct JSON chunk by chunk, and they compile Express from the complete reply.

Express writes one statement per line, in a style close to Python. Each line assigns a component to a variable, and the variable name becomes the component ID. Arguments are positional: the compiler maps them to property names in the order your catalog schema declares them, and _ skips one. $/title binds a value to the data model, and Event("accept") declares a server action. Swappable Inference formats including A2UI Express also work with macros in the Python agent SDK, which help when a screen shows data your systems already hold. The model writes a call with only an ID, such as OrderStatus("ord_42"), and your macro fetches the order and fills in the values, so every value on screen comes straight from your data. The macros README shows the setup.

A2UI Express follows python like syntax and was inspired in part by OpenUI Lang, the language of the open-source OpenUI project, which also writes each component as a name = Component(...) statement with positional arguments. OpenUI Lang adds its own built-in functions and state, and the two languages aren’t yet interchangeable. The OpenUI team has proposed working toward a shared syntax in #3214. Based on our tests; we observed that Express inference format works just as well even with thinking off; which can give you the fastest inference times when working with full expressivity of A2UI.

Some screens have a known shape, such as a settings page, a checkout or a confirmation. For those, the model doesn't need to design a layout. It needs to choose among layouts you have already defined, and a different kind of model is built for that. For this, you would not need the full expressivity provided by A2UI Express.

Jev, from TypeSafe, is what is called a System One model, built to make fast, structured decisions that code can use directly. Jev doesn't generate text or JSON. You send it a state and a set of typed questions, and it answers each one with calibrated probabilities. A question can ask whether a statement is true (Noul), which option from a list fits (Choice), or how something scores on a rubric (Score). Jev answers many questions in one request, in roughly 100 to 300 ms.

Apparite(jev2ui), an open-source design tool, shows one way to connect a System One model to A2UI. Jev decides the structure of each screen, code builds the A2UI components from those decisions, and a small model, gemini-3.5-flash-lite, writes only the text. The questions live in a Markdown grammar written ahead of time. A blockquote asks a question, and the bullets are its options, each with criteria. In one run of 11 prompts, the component tree was on screen in 92 to 298 ms and each screen was complete in 0.8 to 1.7 s. The text writer generated 101 to 341 tokens per screen, and both of Apparite's Jev pipelines produced valid A2UI on all 11 prompts. The project treats these numbers as a first look, since the sample is small.

Controlled generation can only produce the layouts its grammar describes. Apparite's grammar covers nine screen archetypes and twelve blocks, so screens without a known shape are a better fit for Express. A2UI Agent SDKs, don’t include a decision model inference format yet; apparite(jev2ui) project is an example on how A2UI messages could be assembled given a batch of independent decisions from a decision model.

Use Express in your agent. Hill-Climbing Agent Quality with Agents CLI Evaluation

📅 Nov 03, 2026  |  Category: Technology  |  Read Source →

A live walkthrough of the Agents CLI eval loop, from a first run to regression tracking, model-backend experiments, and automated alerting

Building an agent that works on a demo is a different problem from building an agent that stays working across model upgrades, tool changes, and new conversation shapes. The first takes a weekend; the second takes a loop. A team writes test cases, runs them, grades them, reads what failed, changes the agent, and runs the cases again. If the score goes up, the change was good. If it goes down, revert. Over weeks of this, the agent inches toward the ceiling of what the model, tools, and prompt can do together. The quality-engineering name for this is hill-climbing.

The Agents CLI eval namespace was built around this loop. The commands are small and framework-agnostic: eval generate runs the agent against a dataset of cases, eval grade scores the generated traces, eval compare diffs two run results side by side, eval analyze clusters failures into themes, and eval optimize runs an automated hill-climbing pass on the agent's prompt.

Two caveats on this experiment. First, model swaps interact with the prompt: a prompt tuned for a stronger model often leaks capability when ported to a weaker one, so the right comparison is "weaker model with a prompt tuned for it" versus "stronger model with its own tuned prompt." Second, the Vertex AI Eval Service calls a judge model to grade the traces, and the judge is held constant across the comparison. Changing the judge is a different experiment and should be done separately.

Agents CLI does not ship a scheduler, but the eval commands are designed to drop into standard infrastructure. The pattern we can use here is a cron job or Cloud Scheduler trigger that runs eval generate plus eval grade on a cadence and writes the results to a persistent location:

A nightly run against a stable regression dataset catches drift from model updates, data changes in the agent's tools, and dependencies that shift under the agent's feet. For a production agent, the scheduled run also captures the model vendor's quiet upgrades, which can move the agent's behavior without any change on our side. The dataset for the scheduled run is typically larger than the one used in the inner loop (dozens to hundreds of cases rather than a few), since it only runs once a day.

The scheduled run produces a result file every day, but a file nobody looks at is not an alert. The pattern here can be a wrapper script that compares each new run's mean against a baseline (the previous run, or a committed known-good) and exits non-zero when the drop exceeds a threshold. The non-zero exit is what triggers the alert from the surrounding scheduler.

For ADK projects, eval optimize runs an automated hill-climbing pass on the agent's prompt using the GEPA framework (not currently supported for the LangChain extension). The command takes a dataset and a target metric, proposes prompt variants, grades each one, keeps the variants that improve the metric, and iterates. The output is a set of candidate prompts ranked by their eval score, which a human then reviews and promotes to the agent definition.

Two things to understand about eval optimize. First, it is scoped to prompt optimization, not to arbitrary agent changes: the agent's tools, structure, and model stay fixed. Second, GEPA sometimes finds genuine improvements and sometimes finds prompt variants that score higher on the specific metric by overfitting to its wording. The reviewer is the control. For projects where the loop applies, the discipline is to run eval optimize on the regression dataset (where improvements are measurable) and to review the candidate prompts carefully before promotion.

A few patterns and anti-patterns from running this loop ourselves and watching teams do the same.

Lead with a small, representative dataset, not a comprehensive one. The temptation when starting an eval is to try to cover every edge case the agent will ever see. The result is a dataset that takes an hour to run and that nobody runs on a change. Four cases that run in under a minute, as above, exercise the main behaviors and get run on every change. A regression dataset of three hundred cases that runs for an hour becomes a release gate at best and shelfware at worst.

Snapshot result files, not scores. The score is a summary; the result file is the evidence. When a regression surfaces three weeks after a prompt change, having the full result JSON from before and after the change (not just the mean score) is what lets eval compare show the specific case that moved. The per-case breakdown in Step 4 above would not have been possible from scores alone.

Separate the dataset from its expectations. The dataset is the inputs. The eval config is the expectations. They evolve on different cadences: the dataset grows as new real-world cases surface in production, and the config evolves as the team's definition of "good" matures. Keeping them in separate files, both committed to version control, makes it clear which half changed when a score moves.

Treat summary metrics with suspicion. The model-swap experiment in Step 5 is the clearest example. The mean dropped by half a point, but the per-case breakdown showed the drop was concentrated in one case while the others held or improved. A team that only looked at the mean would have made the wrong call.

More evals do not automatically lead to more fixes. A recent controlled study we ran found that coding agents using agents-cli run four times as many evals as coding agents without it, but change the agent after an eval about as often as the baseline. The behavior gain comes from what the skills put into the build at the start, not from the inner iteration. Evals are necessary for quality, but the quality comes from acting on what the evals show.

Build Generative UI Apps with A2UI & CopilotKit Agents

📅 Nov 03, 2026  |  Category: Technology  |  Read Source →

Agent-User Interactions are now evolving from text exchanges to rich UIs. Until recently, most conversations looked like this:

User: "Find me a holiday package to Bali in March." Agent: (six packages in prose, each with dates, hotel, flights, price) User: "The five-night one with breakfast." Agent: "Here's the link. You can book it on the operator's site."

Agents could plan the trip, but everything came back as walls of text. They had no standard way to render a selectable list of packages, a map of the destinations, or a date picker to carry you through the rest of the booking, inside the conversation itself.

Generative UI is the layer that lets agents build interfaces at runtime, shaped by what each request needs - giving users a rich, interactive experience. Implementing that takes two pieces: a way to describe the UI and an agentic stack that connects your agent to your application and renders that UI.

Generative UI covers a spectrum of approaches, from using predefined higher order components, to enabling your AI agent to have the flexibility to decide how to build the UI.

At the controlled end, you build each component ahead of time, and the agent picks which one to render and with what data. It's brand-safe but it does not allow for deep customization and personalization based on the user’s intent. At the open end, the agent returns a raw UI program written in HTML, Javascript and/or Dart that renders inside a sandboxed iframe. That covers anything you did not plan for, at the cost of a surface that drifts from your design system and executes code a model wrote.

A2UI works through the entire spectrum. It participates in controlled generation with decision models like Typesafe’s Jev and also open-ended code generation that may output A2UI JSON messages. The declarative mode, where agents assemble pre-declared components and functions, is the most popular. A2UI is the framework-agnostic standard for declaring UI intent, so local or remote agents can generate your UI from your existing component catalog using a common language.

Frontend developers can now ship the building blocks once, and the agent composes them for each request.

The Basic Catalog ships 18 general-purpose primitives across layout, display, input, and containers. The agent can compose entirely different interfaces from the same 18 primitives, depending on what the request needs.

CopilotKit is built on AG-UI (Agent-User Interaction Protocol), which supports A2UI payload and provides Agent SDKs across many agentic backends.

Your agent emits A2UI operations. AG-UI carries them to the client as typed events. When the user takes any action, the values are sent back along the same stream.

A2UI works with any AG-UI compatible agent. Frameworks like Google ADK, LangChain, Mastra and Strands are all AG-UI compatible, so the setup is identical whichever one your agent runs on.

Trusted SSL Certificates for Localhost

📅 Nov 03, 2026  |  Category: Technology  |  Read Source →

Posted on Nov 3 • Originally published at kevinleary.net

The best way I’ve found to add SSL certificates to a localhost environment is using mkcert, which is technically not a self-signed certificate at all. Instead, it creates a local certificate signing authority, adds it to your machine, and uses that to sign certificates. The end result is a fully valid SSL certificate that is not self-signed, so it works with modern browsers and aligns with security protocols that block self-signed SSL certs.

mkcert is an open source command line tool written by Filippo Valsorda, a cryptographer who spent years on the Go security team at Google. As described on GitHub, it’s:

a simple tool for making locally-trusted development certificates that requires no configuration.

Under the hood it does two things. First, it generates a private certificate authority (CA) that lives only on your machine and installs it into your system and browser trust stores, the same lists of trusted authorities that let your browser trust certificates from Let’s Encrypt or DigiCert. Second, it signs leaf certificates with that CA for whatever hostnames you ask for. Because the signing authority is trusted by your machine, every certificate it issues is trusted too: real HTTPS, green padlock, no warnings, no exceptions to click through. This is fundamentally different from the classic openssl self-signed certificate. A self-signed cert has no authority behind it, so browsers correctly treat it as untrustworthy. mkcert gives you the full chain of trust, just scoped privately to your computer. The private CA key never leaves your machine, which is also why this is safe: nobody else’s browser will ever trust certificates signed by your local CA.

mkcert supports Mac, Windows and Linux machines, so it should work with your setup.

What a killed Playwright script leaves behind on Linux: processes, profile dirs and a SIGTERM that does not exit

📅 Nov 03, 2026  |  Category: Technology  |  Read Source →

A Playwright script ends in more ways than await browser.close(): it throws, someone calls process.exit(), a container runtime sends SIGTERM, the OOM killer sends SIGKILL. I wanted to know what each of these leaves behind on a Linux host: running Chromium processes, temp directories, or a Node process that ignores the signal.

I ran all of it on 2026-11-03: Linux 6.8, Node v24.22.2, Playwright 1.63.0 with the bundled chrome-headless-shell (revision 1243). Everything below is that one machine and one browser build. Containers, systemd, macOS and Windows are not covered.

The child script launches a browser, opens a page, prints READY, and then either waits for a GO line on stdin and ends in a chosen way, or hangs so that the harness can send it a signal. The cdp mode does not launch anything: it attaches to a Chromium that the harness started separately, which is what many browser pools do.

The harness reads the process tree from /proc while the child is running, ends the child, waits three seconds, and then checks which of those PIDs are still alive (zombies do not count) and whether the browser's profile directory is still on disk. It kills and deletes only what it started.

In the cdp rows the first count was 14 or 15 and the second 10 or 11 across my runs, so read that as "most of the tree stays". The other rows were identical on every run. In the cdp rows the profile directory belongs to the browser the harness started itself, and it is still there because that browser is still running.

Playwright's own launch cleans up after a crash, even after SIGKILL. throw, exit and SIGKILL all end with zero Chromium processes. In a one-off check (script not included) I printed the command line of the launched browser, and it ends in --remote-debugging-pipe. I did not trace the mechanism, but it fits a browser that exits when the other end of its pipe closes. The cdp rows are the contrast: that browser listens on a port, and nothing ties it to the script. In the same one-off check, chromium.launchServer() also left no processes after SIGKILL, so it is not only launch().

Browsers you did not launch are not cleaned up at all. In the cdp rows, about ten Chromium processes stayed alive after browser.close() and after SIGKILL. This is the case where a leak actually happens. The docs for browser.close() say that for a browser you connected to, it "clears all created contexts belonging to this browser and disconnects from the browser server". It does not stop the browser. Whoever started it owns its lifetime. If you run a pool this way, you need a supervisor that restarts or kills the browser itself, and a periodic check that counts processes.

SIGKILL leaves the profile directory. The launch SIGKILL row says profile dir left: true. Each one was about 224 KB in my runs, which is nothing for a single crash and something for a worker that gets OOM-killed a few times a day on a small /tmp. A normal close(), an exception, process.exit(), SIGTERM and SIGINT all removed it. I did not look into which Playwright process does the deleting. Whatever it is, SIGKILL gives it no chance to run.

launch SIGTERM says node: still running. The child had a setInterval standing in for an HTTP server, and after SIGTERM the browser was gone but Node kept going. The reason is the handleSIGTERM launch option, which defaults to true and is documented as "Close the browser process on SIGTERM". Playwright installs a handler that closes the browser. Node's documentation says that once a SIGTERM or SIGINT listener is installed, the default behaviour (exit with code 128 plus the signal number) is removed. So the server stays up with no browser behind it. SIGINT ended with exit code 130 in my run; I did not look into why it differs from SIGTERM.

I did not test what Docker or Kubernetes do from here. The consequence I can state from this measurement is only that a service which does nothing on SIGTERM keeps running with a dead browser, and anything that waits for it to exit has to fall back to SIGKILL.

This is the service skeleton I used to test two remedies: close the browser and exit on SIGTERM and SIGINT, and sweep profile directories that nothing is using when the service starts.

The sweep treats a directory as stale only if no process on the machine has it in a --user-data-dir argument and it is older than a minute. Chromium rewrites its own argument list with spaces on Linux, which is why the pattern stops at whitespace and not only at the NUL byte. I found that when my first version of the harness reported "profile left: false" for a directory that was plainly still there.

To test it I used a second script that is not included: it starts the service, SIGKILLs it, starts it twice more, sends SIGTERM to both, and counts new profile directories under /tmp each time. The sweep deletes everything under that prefix that no process references, so the test script lowered the age limit to five seconds and waited six. Results:

After SIGKILL one profile directory stayed. The next start swept it (swept stale profiles: 1). Two live services each kept their own directory, so the sweep did not touch a running browser. Both services exited with code 0 on SIGTERM, in 106 to 281 ms across my runs, and no new directories were left.

Sources: Playwright BrowserType launch options for handleSIGTERM and handleSIGINT, the browser.close() text from the Playwright 1.63.0 type definitions, and Node.js process signal events.

Chord Buys Its Rival Zenlytic To Build An Agentic Version Of A CDP

📅 Nov 03, 2026  |  Category: Technology  |  Read Source →

Two data infrastructure startups with agentic commerce ambitions are combining forces.

On Tuesday, Chord, a six-year-old commerce tech startup, acquired Zenlytic, an AI startup with an anthropomorphized data analyst agent named “Zoë,” for $5 million.

Chord’s co-founder and CEO, Bryan Mahoney, told AdExchanger that the combined business has around 30 full-time employees and some 60 customers, with an annual run rate nearing $10 million.

Chord launched as a “headless commerce” software company, Mahoney said.

At the time, the headless approach was catching on with Shopify merchants and social-native sellers. The idea was to decouple the front-end website from back-end fulfillment, making for a more agile business and faster-loading pages at a time when Google’s SEO prioritized speed. Shopify has since addressed the problem by taking steps to make its own storefronts faster.

Since the rise of LLMs, Chord and Zenlytic have both pivoted to become explicitly AI-based data infrastructure services. For instance, Mahoney said, Chord is now paid on a usage basis rather than traditional subscription pricing. And because pricing is usage-based, Chord closely tracks how often users prompt its AI agent for an answer – a rate that has accelerated to about once every 20 seconds, he said.

Although the more people use agents, the more ways they find to abuse them.

Mahoney pointed to a recent story in which someone figured out they could use McDonald’s online customer support and ordering agent to answer demanding math and computer science questions – a workaround to having to pay for one’s own AI tokens. (McDonald’s has since fixed this, by the way.)

Chord guards against this kind of misuse. It’s trained its AI agent with the necessary context so that off-base prompts return a response that this isn’t the right agent for the task. That includes requests to use its agent “like a therapist,” say, or for something like “make these results look better to a CFO,” Mahoney said.

Those guardrails matter more as Chord’s business shifts.

The business model is now more like an agentic version of a CDP, Mahoney said. For example, Sonos, a Chord client, can use it to track customers and enrich first-party data, such as understanding when customers are moving to a new home – an opportune time to send emails or SMS notifications about new products.

The data analyst agent “largely replaces” Chord’s own analyst agent, Mahoney said.

Guess human data analysts aren’t the only ones who need to be worried about being replaced by AI. Even agents can be put out of work.

But Chord also has other agents that work better alongside Zoë, Mahoney added. Chord has gone deeper into commerce infrastructure, for instance, with use cases geared toward Shopify-type businesses, and customers using the Snowflake data warehouse in particular. Zenlytic, by contrast, has tended to work with large enterprise brands of all kinds, not just in ecommerce, and supports many more cloud data warehouses.

The goal, Mahoney said, is for some of Zenlytic’s large customers, including Black & Decker, Verizon, J.Crew and Stanley, to adopt Chord’s data infrastructure and activation, including the ability to segment profiles or audiences for campaign targeting and measurement.

But winning over large brands requires confidence in the technology, and right now there’s an odd mix of growing trust and distrust of AI agent outputs.

Mahoney noted that the outright “hallucinations” of earlier LLMs have become relatively rare. “Now it might be more like a lucid dream,” he said. The outputs are believable and often can feel correct.

And so marketers need to be aware that a confident-sounding AI agent can still lead them badly astray. It’s a concern Mahoney shares.

“We constantly [need to] evaluate the answers that we’re getting back to make sure that the way we’re using AI is increasing confidence on a daily basis, not getting eroded,” he said. “These are some of the things that keep me up at night.”
